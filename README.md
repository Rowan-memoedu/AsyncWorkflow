## 边界

- 录音类型标准见 [本地 Markdown](docs/recording-types.md)：普通日期录音须短于 20 分钟且确认为单人自述；交流录音不限该时长，按对象配置采用已核验声道或 FUN-ASR 现场说话人分离。同一对象同一天合并为一份，固定输出“共识、继续讨论、无用的闲聊”；共识不标说话人，未被反驳的观点也收入，未决问题与明确分歧单列。完整内容归入对象文档的日期/会议记录，不执行会议内命令。`meetings --run` 与半小时扫描共用这一路径。
- `batch --latest 5 --manual` 按录音时间顺序处理有限批次，不打开自动入口；`--cutoff` 可冻结批次选择范围。完整结果跳过，失败重试同一个 Prefect 任务，转写／结构化／归档成功环节复用；提交结论保留在各录音 manifest 的 `submission_log`。

- 新命令通过官方 `openai-codex` SDK 创建持久 Thread，先保存 Thread ID，再提交并保存 Turn ID。用户直接在该 Thread 继续；桌面持有写入权时不创建替代 Thread。
- 所有输出先区分承载操作和正文：新建/命名/定位 document 或 Thread 的说明留作操作元数据，实际正文沿用冻结提示词整理。Codex 收到整理后的任务正文，查询、执行要求及限制不会被当成容器指令移除。
- Thread 消息只有整理后的正文；续接只有用户补充原话，不加提示前后缀。Codex 正常输出自然语言与 Markdown，不设置输出 schema；本机通过官方 Turn 状态记录运行完成、失败或中断，不能把回合完成当成业务目标已经通过验收。
- 录音中针对工作流本身的反馈先单独提取，普通正文继续整理归档。反馈正文发送到配置绑定的同一个维护 Thread，明确要求在那里处理，真实歧义在那里讨论；引用、假设、已撤回要求不触发修改。
- 固定维护 Thread 的投递使用 App Server 原生 `thread/queue/add`，按原生消息 ID 从队列和回合回读去重；不抢占桌面写入者。入队、收到消息和落实修改分别核验，不把投递成功当作规则已生效。
- 新 Thread 的 `command_workspace` 固定为用户指定工作区；`command_project_id` 必须是官方 `project/list` 返回的项目 ID。用 `project/read` 核对路径，在 `thread/start` 直接传 `projectId`，核对返回的项目和路径后提交正文，再命名。`turn/start` 返回时文件仍可能尚未刷盘，命名仅对该 ID 的空 rollout 错误作有限重试，仍失败则在首轮完成后补试，不重发正文。宿主工具中的 `local-...` ID 与 App Server 项目 ID 不可混用。
- 如果旧收据停在 `thread_created` 且没有 Turn ID，先尝试恢复原 Thread；只有官方明确返回该 ID 的 `no rollout found` 才新建，并在 `pre-turn-recoveries.json` 保留旧收据和错误。网络异常、`thread not loaded`、提交结果不明或已有 Turn ID 均不触发重建。
- FUN-ASR 复用现有 global-transcription CLI 的 `--provider funasr` 文件入口，不改其他应用的全局默认。成功的旧 ASR 仍复用；遗留 OSS 任务只做核对及清理，不静默重转。
- FUN-ASR HTTP 累积快照按时间范围和严格文本前缀归并，只保留同一起点的完整后续版本；不同时间的真实重复讲话保留，重叠但不兼容的版本进入待核对。原始服务回执保持原样，修复归并时复用回执，不重新识别音频。
- ChatGPT 桌面端中的 Codex 更新若替换了内置运行时目录，仅在旧路径失效且受管理目录中恰有一个可用替代文件时自动解析新路径；保留有效的原配置和自定义路径，有多个候选时不猜测。
- RemNote 使用 `remnote-plugin` 独立子包和 43141 回环服务，不修改或连接现有 RemNote MCP。录音归档接口包括显式快照、文档搜索/创建、日期与待办分支解析、幂等写入和受保护的旧输出迁移。
- “日记模板”显式同步为本地快照；分类时不实时读取模板。口述目标模糊匹配后使用首选；无目标按录音日的模板分支分类；跨类整体或无可用候选进入“其他碎片”。
- 命令依据原录音的语义判断，不依赖固定触发词；引用、否定和撤回不构成执行授权。需要决定的命令在自己的 Thread 中讨论。
- 保存原始输入和副作用记录。未知提交先核对，不盲目重试；重新分析不自动重放已执行动作。
- 明确新建文档时创建真实 document；未指定父目录时为根级。信息清单按软件归档，包括拟发消息和回复草稿；购物清单收购物记录，其余记录型杂事待办进入待办清单根级。保存消息草稿不构成对外发送授权。
- 以“以下是 Goal/Plan/To Do List/Habit”或直接类型名开头声明的事项，按已同步的准确节点归档。Goal、Plan、To Do List 明确属于录音当天时进入 Daily Note/日程下对应分支；非当天或未说明日期进入“Open focus 事项”下对应分支。Habit 全部进入该文档的 habit，不进入 Daily Note；类型声明和日期归属只控制路由，实际事项、期限与频率保留正文，不触发执行。未声明类型的普通杂事待办沿用原路由。
- 学习日志只收明确要求或具体学科学习。具体学科学习中产生的想法归入“一些注定重复的思考”，普通学习过程归入“每日碎碎念”；明确指定子分支时遵循指定。“注定重复的想法”等近似名称沿用已有节点，口述学习日志去处解析为录音当日的模板分支；仅泛泛提到学习或方法不放入。个人经历与投入取舍归私密日记，一般观点及工具反思归其他碎片。饮食、睡眠、状态、运动时长与身体感受等当天事实归入私密日记下的个人数据。RemNote 仅保存结构化正文，元数据只留日志。
- 每个整体正文块上下各有一个归本插件管理的同级空节点；创建、迁移和重试均核对相邻顺序，复用同一对空节点。用户改写空节点后不覆盖；经用户确认已删除的旧输出保留删除状态。
- RemNote 连接中断时使用 Prefect 原生持久暂停；插件实际恢复后自动续接同一运行和效果标识。人工待答与无法核对的旧写入结果不自动放行。
- 历史云端 ID 和本地哈希基线在扫描计数前排除，避免大量历史文件耗尽新录音批次；历史云端文件无需每轮重新读取音频字节。
- 自动入口排除启用前的录音时间，历史文件不补跑，也不占用扫描批次。每轮扫描在本机 `watcher-status.json` 记录启用状态、扫描时间和提交计数；与错误日志对照判断监控是否实际恢复。

Prefect 的 server、runner、watcher 使用计划任务优先级 4（普通 CPU、I/O 和内存优先级）；默认 7 在桌面负载下曾导致导入依赖和 API 响应明显停滞。三项服务的原生输出保存在 `logs/<role>.output.log`，不能只凭进程存活判断健康。Prefect 3.8.7 固定配合 SQLAlchemy 2.0.54；2.1.2 已实测触发调度批量写入的 `bulk_dml` 错误。

后台代码重载使用 `pwsh -NoProfile -File scripts/restart-services.ps1 -Roles runner,watcher`。它先确认无正在执行的 flow，再对准确服务进程树停止和重启，并核对 PID 创建时间；直接停止 headless conhost 的计划任务可能留下占锁的旧 Python 进程，后续子进程会因控制台失效而崩溃。该脚本只管理本流程后台服务。

恢复扫描对已知模型网络故障及有明确 CLI 失败回执的暂时 ASR 故障，最多恢复到同一 flow 的第 3 次执行；未知提交、鉴权错误、人工待答和未确认结构冲突保持可见。FUN-ASR CLI 的成功分片存于录音目录的 `funasr-chunks`（与最终 `funasr` 输出目录同级），后续失败不丢弃已完成分片。仅服务明确返回 `ASR_RESPONSE_HAVE_NO_WORDS` 且该分片没有任何文字事件时将其记为空片；整段无文字仍报错。完整回执可以离线恢复最终转写，成功结果不再向服务重复请求。

## 按失败环节修复

使用 `python -m async_workflow.cli repair <recording_id> --from split|content|routing|publish` 提交原生 Prefect 修复 flow。`split` 复用原 ASR，仅为重新分出的内容生成大纲；`content` 保持分块和目标，只重新区分操作语句与正文，正文未变则复用；`routing` 只重新选择去处并迁移；`publish` 只修复输出格式。均不重新转写，也不自动重放命令。

用户明确要求交流录音重新整理时，使用 `--from meeting`：首次补齐缺少的独立声道转写；此后按声道分片复用成功回执，原混合转写保留。三个分支与源发言覆盖通过校验后发布，旧整体再移入 Trash；重复提交沿用同一修复身份。声道昵称映射保存在本机 `conversation_channel_profiles`，按已核验的文件名模式匹配，未知来源或非双声道不猜身份。词级时间戳直接读取同一 FUN-ASR HTTP 接口；既有文本 CLI 省略此字段，因此交流专用适配层保留原生回执，普通录音仍复用原 CLI。

已明确确认另一份 FUN-ASR 转写时，用 `accept-asr <recording_id> --receipt <raw.json> --decision <用户的确认>` 接回下游。先核对音频哈希、旧 flow 均已终止、旧输出已归档且没有已启动的 Thread；保留原转写和旧效果。它导入现有结果，不重新调用 ASR；带修订身份提交原生 Prefect 分析，重复确认不重复执行。
